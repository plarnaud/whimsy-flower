behave differently — 0 overlap with the Hudson Valley pillar, but because they're **regional**, not
single-town, queries, each represents genuine, addressable search demand rather than a doorway-page
trap. These inform the two conditional regional spokes in §3.

## 4. Quality-gate ruling: no per-town pages

Per the brief's explicit constraint and confirmed by SERP data in §2: **do not build dedicated pages
for Rhinebeck, Kingston, Beacon, Woodstock, New Paltz, Millbrook, or Albany.** All seven return
near-100%-different, hyper-local-directory-dominated SERPs with no realistic path to ranking and no
genuine unique content to differentiate seven pages from one studio location. Mitigation instead:

1. `areaServed` array in `Florist`/`LocalBusiness` schema listing all seven towns + Hudson + the
   Catskills + NYC (already drafted in `schema.md`).
2. One FAQ block on `/weddings` (or a shared component rendered on `/weddings` + `/events`) with
   ~7 short Q&As in searcher's voice: *"Do you travel to Rhinebeck / Kingston / Beacon / Woodstock /
   New Paltz / Millbrook / Albany for weddings?"* — answered on-brand ("We travel throughout the
   Hudson Valley and the Catskills for the right celebration...").
3. Real per-project location detail folded into existing gallery entries (`galleries.ts` already has
   a `location` field, e.g. "Pennsylvania," "2025" — replace placeholder/date-only values with actual
   town names where true) and into `alt` text, which `local.md` separately flags as currently
   geo-blank.

This keeps the long-tail geo volume addressable without tripping the thin/doorway gate this skill and
`sitemap.md`/`local.md` both enforce.

## 7. "Florist" word-dependency by cluster

Building on `content.md`'s workaround catalogue (title/meta/schema/alt-text/FAQ-in-searcher-voice),
here is which clusters in this plan are most exposed to the banned word:

| Cluster | Dependency on literal "florist" | Why | Where it's safe to use the word |
|---|---|---|---|
| Core Weddings (`/weddings`) | **High** — "florist" is the head noun in the majority of high-signal variants (hudson valley wedding **florist**, best wedding **florist**, wedding **florist** near me) | Directory/aggregator competitors (The Knot, WeddingWire, Zola) rank almost entirely on exact-match "florist" pages | `<title>`, meta description, `Florist` schema `@type` (per `schema.md`), image `alt` text, one FAQ question in searcher's voice |
| Regional (Catskills, NYC) | **Medium** — competitor set mixes "florist" and "floral designer" roughly evenly (Rachel Cho: "Luxury Florist NYC"; Floraland: "floral design"; Gathering Florist: "floral designer") | More synonym tolerance in this SERP than the core cluster | `<title>` tag, schema, alt text |
| Elopement & Micro-Wedding | **Medium** | Same directory pattern as core cluster, smaller volume | `<title>`, schema |
| Ceremony Installations | **Low** | Query is style/concept-led ("installation," "arch," "sculptural"), not vendor-category-led | Rarely needed |
| Editorial & Brands | **Low** | Competitor language already favors "floral designer" / "stylist" (Gathering Florist's own about page uses "floral designer") | Optional in meta only |
| Experiences (workshops/flower bar) | **Very low** | Head nouns are "workshop," "class," "flower bar," not "florist" | Not needed |
| Journal (Investment, Seasonal) | **Low** | Informational queries, no vendor-category head noun | Not needed |

Net: the banned-word conflict concentrates almost entirely in the **Core Weddings** pillar. The
existing `content.md` workarounds (title/meta/schema/alt/FAQ) fully cover it without touching visible
